# TripBeam 城市旅行 Agent 体验迭代

## 产品定位

面向陌生城市中只有 30–240 分钟可用时间、偏好尚不清晰的临时出行用户。用户从一句话开始，通过必要追问确认出发条件，比较不同路线，调整地点和顺序，再保存并分享行程。

这轮交付以现有 React、Fastify、地图适配器与确定性规划器为基础，补齐会话延续、决策信息、编辑异常恢复和移动操作的体验。规划事实仍由地图查询和规则校验提供。界面的处理记录来自服务端返回，不展示伪造的实时阶段或百分比。

## 四个连续场景

| 场景 | 关键决策 | 页面回应 |
| --- | --- | --- |
| 说说想法 | 我需要提供什么？ | 对话、单项追问和可编辑的五项偏好摘要；手动选择入口；会话恢复与请求重试 |
| 比较方案 | 不同路线差在哪里？ | 主题、地点序列、总时长、距离、步行强度和余量；展开推荐依据；地图聚焦；差异表 |
| 调整行程 | 修改后是否仍然可行？ | 交通分段、停留时段、时间分配；增删替换和排序；自然语言调整；无效草稿原因及恢复入口 |
| 保存与分享 | 同行的人能看懂并带走吗？ | 固定版本快照、地图、时间清单与出发提醒；复制链接、复制清单和复制失败的手动操作 |

## 设计约束

- 以暖白、深绿与低饱和路线色保持连续视觉；用文字和图形共同表达选择和状态。
- 首页主栏负责对话，侧栏展示用户已确认的信息。移动端改为单栏，所有流程均能通过触控与键盘操作。
- 对比页先展示决策信息，地点证据折叠收纳。地图聚焦与进入编辑分为两个明确按钮，避免按钮嵌套。
- 时间分配明确区分路上、停留、缓冲和剩余可用时间。所有数值由返回的路线数据计算，不由模型补造。
- 编辑时以地点 ID 保持当前选择，删除后选择有效的首个地点，避免索引越界。
- 无效草稿和有效路线明确区分：展示拟编辑地点、违反约束原因；地图保留有效路线；恢复前不能保存分享。
- 请求失败保留可见原因和重试入口。复制失败提供可选中的文本，不静默失败。

## 本轮验收清单

1. 自然语言输入后，缺少的字段可逐项补充；已经确认的条件在偏好摘要中可见。
2. 完成规划后可以对比实际返回的 1–3 条路线；降级结果清楚说明可选路线有限。
3. 聚焦方案 B 后请求解释，仍保持方案 B 的选择；生成新行程时进入新行程对比。
4. 编辑清单能够查看每段交通时间、距离、到达与离开时间，并可增删、替换和排序。
5. 自然语言处理期间禁用其他编辑、保存和分享操作，避免同一版本并发修改。
6. 超时编辑返回无效草稿时，页面不显示“修改已通过”；保存分享不可用；恢复按钮可恢复到有效路线。
7. 删除最后一个选中地点或切换方案后，地图与替换入口仍指向存在的地点。
8. 保存当前版本后可以创建分享快照；后续修改不会更改旧快照。
9. 分享页可复制链接和可读清单；浏览器不允许复制时可手动选择内容。
10. 窄屏中无页面级横向滚动，固定底部操作不遮挡最后的内容；按钮、表格与地图均可使用。

## 能力边界与后续优先级

本轮未新增预算约束、实时营业/预约、实时交通、导航指令、自动删减或用户账户。界面不得声称这些能力已可用。当前路线为单次短途规划，不覆盖跨日旅行。

下一轮应优先基于真实用户任务验证“从一句话到选定路线”的完成率和耗时，并分别记录模型耗时、地点查询、路网重算和失败恢复。预算和同行者约束需要先定义可验证的数据来源和可执行规则，再进入前端收集。附件中的历史测试成绩不作为本轮的测量结果。
